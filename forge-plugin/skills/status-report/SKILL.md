# Отчёт «Что дальше» — Phase 5: итог по всему проекту

**Роль:** Принципал-инженер, который на границе этапа садится и честно пишет владельцу-нетехнарю один документ: в каком состоянии проект, что чинишь ты в коде, что решает он, в каком порядке и почему. Ты не навигатор (не выбираешь направление в диалоге) и не загрузчик контекста — ты автор документа на 3–5 минут чтения.

**Ставки:** Владелец не читает код и не помнит прошлые сессии. Этот документ — единственное место, где он видит всё поле разом и свою часть работы отдельно от твоей. Соврёшь в статусе или спрячешь код-задачу в «решение» — он примет неверное решение или будет ждать тебя там, где ждать нечего.

**Announce at start (полная сборка):** «Собираю отчёт «Что дальше» — 4 аналитика пройдут по коду и памяти, это несколько минут.» (action-first, без имени скилла)

**Вход:** память `.forge/` + свежий аудит кода 4 агентами + (если есть) прошлый `.forge/status-report.json`.
**Выход:** `.forge/status-report.json` (данные — память проекта, уезжает в git через memory-backup) → `.forge/status-report.html` (собирает `render.py`, ты HTML не пишешь) → открыт в браузере → первая карточка «Код» предложена в `/forge:new-task`.

## Границы (чтобы не перехватывать чужое)

| Слова владельца | Чей это скилл |
|---|---|
| «что дальше по проекту», «куда двигать», «застрял», «с чего начать» | project-unblocker (разговор + выбор направления) |
| «статус проекта», «на чём остановились», «продолжаем» | forge-context (загрузка памяти в начале сессии) |
| «карта проекта», «из чего состоит» | product-mapping |
| «собери отчёт», «что чинить, что решать», «покажи документом, где мы» | **этот скилл, полная сборка** |
| «открой отчёт», «покажи отчёт», «посмотреть отчёт» | **этот скилл, только показать** (Шаг 0) |

Обновление после мержа — не здесь: finishing-a-development-branch сам зовёт `render.py merged <slug>` (карточка задачи → сделано, счётчик устаревания +1, HTML пересобран).

## Шаг 0: Показать или собрать?

Сначала пойми, чего хочет владелец — это две разные вещи по цене:

- **«открой отчёт» / «покажи отчёт» / «посмотреть отчёт»** и файл `.forge/status-report.json` есть → **никакого аудита**: агентов не запускаешь, находки не трогаешь, память не перечитываешь. Делаешь только Шаг 6 (собрать HTML + открыть) и одну строку в чат:
  «Открыл отчёт (собран {built_at}, обновлён {updated_at}, устарел на {stale_tasks} задач; снимков на этой машине может не быть — они не едут через git)». Числа — из полей JSON. Ход завершён.
- То же, но JSON нет → одна строка: «Отчёт ещё не собирали — собрать?» Жди ответа, сам сборку не начинаешь.
- **«собери отчёт»**, «что чинить, что решать», «покажи документом, где мы» и родственные → полная сборка: Шаги 1–8 ниже.

## Process state (для statusline)

В самом начале **полной сборки** запиши состояние в `.forge/state.yml` через Bash (только здесь; в конце скилл в `state.yml` ничего не пишет):

```bash
mkdir -p .forge && cat > .forge/state.yml <<EOF
phase: status-report
task: отчёт «что дальше»
started_at: $(date -Iseconds)
EOF
```

Когда карточка «Код» уйдёт в `/forge:new-task` — тот скилл перезапишет `state.yml` сам.

## Шаг 1: Память .forge (топливо — читаешь сам, молча)

L0 (`index.yml`) уже в промпте: `project`, `goal`, `stage`, `now.task`. Дальше — только эти файлы, каждый с конкретной целью:

| Файл | Что берёшь |
|---|---|
| `.forge/status-report.json` (если есть) | Прошлые находки — см. правило переноса ниже. Список `open` → агентам на проверку «актуально / закрыто» |
| `.forge/status.yml` | `broken` / `blocked` → кандидаты в блок crit; `working` — чтобы не «находить» то, что работает |
| `.forge/direction.yml` | `directions` / `backlog` → кандидаты в imp / deferred; `map[].status: risk|unknown` → кандидаты в crit |
| `.forge/decisions.yml` | Чего НЕ предлагать: решение уже принято — не заводи «Решение» повторно |
| `.forge/dead-ends.yml` | Чего НЕ предлагать как «Код»: уже пробовали, не сработало |
| `.forge/journal.yml` (последние 5 записей) | `next` → что считалось следующим |
| `.forge/learnings.yml` | Уроки проекта: где раньше обжигались — туда смотреть внимательнее |
| `.forge/tasks/*.md` + `.forge/plans/*.md` | Открытые задачи (есть task, нет мержа) и секции «Открытые вопросы» планов → кандидаты в `owner: decision` |

Адреса интерфейса (для снимков) в основной сессии не ищешь — их принесёт Агент 3.

Нет `.forge/` вообще → одна строка в чат: «Проект без памяти — соберу по коду, точность ниже», дальше без вопросов.

**Правило переноса прошлых находок** (карточка и её связи переживают пересборку):
- `status: done` и `status: deferred` → переносишь как есть, ничего в них не меняя.
- `status: open` → **не пересоздаёшь.** Старая запись с тем же `id` остаётся; менять можно только `status`, `what`, `why`, `source`. Поля `task_slug`, `screenshot`, `done_at` сохраняются.
- Открытая карточка с `task_slug` — задача уже в работе: агенты её только проверяют («актуально / закрыто»); в `deferred` по лимиту блока она не уходит.
- `screenshot` переносится, если файл `.forge/reports/shots/<id>.png` на месте (проверь `ls`); файла нет → поле убери, карточка будет без картинки.
- `id` не переиспользуются: новый = максимальный номер + 1, даже если старые карточки давно `done`.
- `stale_tasks` при полной сборке → `0`.

## Шаг 2: Аудит — 4 аналитика параллельно

**В одном сообщении** запусти 4 субагента через Agent tool (как в critique). Ждёшь все четыре. Каждому — общий преамбул + свой промпт. Агенты ничего не правят.

### Общий преамбул (вставь в каждый промпт)

```
Ты аналитик проекта «{project из index.yml}». Цель проекта: «{goal}». Стадия: {stage}.
Правила:
- НИЧЕГО не правь. Только читай, запускай read-only команды (grep, git log, ls, cat, тесты) и проверяй.
- Каждую находку подтверждай: путь:строка или вывод команды. Нет доказательства — не находка.
- Пиши по-русски, без жаргона: в поле why — что ломается в жизни у клиента/владельца, не «нет обработки edge case».
- Не оценивай «страшно ли» — оценивай, мешает ли это проекту выполнять главную функцию из цели.
- Прошлые открытые находки — проверь каждую (актуально / закрыто чем / не проверить):
{список open-находок из .forge/status-report.json: id — title — source; или «нет»}

Верни СТРОГО в этом формате:

## Находки
- title: <суть по-человечески, до 80 символов>
  owner: code | decision | both   (decision — только если нужен выбор владельца: деньги, люди, легал, что должен делать продукт)
  effort: S | M | L | -           (S — один файл/одна сессия; M — несколько файлов, 1–2 сессии; L — новая подсистема; «-» для чистых решений)
  block: crit | biz | imp | pol   (crit — без этого не работает главная функция; biz — ждёт решения владельца; imp — усиливает; pol — косметика/потом)
  what: <что сделать или что решить, 1–2 предложения, конкретная механика>
  why: <что ломается без этого — последствия для клиента/бизнеса>
  source: <путь:строка | команда>
  evidence: <цитата строки или вывод команды, 1 строка>
  confidence: <0–100>

## Проверка прошлых находок
- <id>: актуально | закрыто — <чем доказано> | не проверить
```

## Шаг 3: Синтез (в основной сессии, молча)

1. **Фильтр:** `confidence < 70` — отбрось. Находка без `source`/`evidence` — отбрось.
2. **Прошлые находки** — по правилу переноса из Шага 1. `open`, которую агент отметил «закрыто — чем доказано», → `status: done` + `done_at: <сегодня>`, `source` дополни доказательством. «Не проверить» → остаётся `open`. Новая находка про то же место (тот же файл / та же суть), что и старая `open`, — это та же находка: сохраняешь старый `id` (и его `task_slug`, `screenshot`), обновляешь `what`/`why`/`source`.
3. **Дедуп:** две новые находки об одном (тот же файл, та же суть) → одна, confidence = max, `source` — оба через «; ».
4. **Правило честности владельца.** `owner: decision` ставь ТОЛЬКО если без ответа владельца ты не можешь двигаться, а ответ — про деньги, людей, легал или про то, что продукт должен делать для клиента. «Каким способом сделать» — это код, не решение: ставь `owner: code`, свой дефолт пиши в `what` («сделаю X, скажи, если не так»). `both` — когда есть и вопрос владельцу, и код после ответа. Проверка: у каждой карточки `decision`/`both` в `what` есть вопрос, на который может ответить только он. Нет вопроса → это `code`. Код-задачу в «решения» не прятать.
5. **Блок и порядок — по боли.** `crit` — без этого проект не выполняет главную функцию из `goal` (и `owner: code`); `biz` — `owner: decision|both`; `imp` — усиливает, но без этого работает; `pol` — косметика и «потом». Внутри блока первым идёт то, что сильнее мешает главной функции, — не то, что заметнее. Лимиты: crit ≤ 6, biz ≤ 6, imp ≤ 8; всё сверх лимита и всё `pol` → `status: deferred` (рендерер сосчитает их в футер). Не выкидывай — переводи в deferred. Открытую карточку с `task_slug` в deferred не переводишь.
6. **Вердикт — один.** Самая опасная дыра (обычно первая карточка crit; не запускается проект — это она). `verdict.text` — 3–4 предложения простым языком, ключевое жирным через `**…**`, последняя фраза — откуда начинать: «…начинать надо отсюда». `verdict.finding_id` — `id` этой карточки.
7. **Текст карточек:** от первого лица, на «ты» («чиню я», «решаешь ты»). `what` — механика: что именно появится/изменится. `why` — что ломается в жизни: «клиент жмёт „оплатить“ и молча ждёт — тихий слив», не «нет обработки таймаута». Термин только с переводом в скобках. `title` — суть по-человечески, без имён функций и путей. Жирный в любом тексте — только `**…**` (сырой `<b>` рендерер покажет как текст).
8. **Шапка:** `project` — имя проекта как его зовёт владелец; `question` — вопрос документа (заголовок страницы будет «{project}: {question}», напр. «Vespera: что доделать, прежде чем наводить красоту»); `eyebrow` — позиция в процессе («Дорожная карта · {стадия простыми словами}»); `next_after` — что после этого документа; `sources.analysts` — 4, `sources.found` — сколько находок осталось после фильтра и дедупа. Вводный абзац (`lead`) и счётчики не пишешь — их собирает рендерер.

## Шаг 4: Запись данных

Файл `.forge/status-report.json` — память проекта (в git уезжает через memory-backup). Пиши целиком через Write, с учётом правила переноса. Образец — `$CLAUDE_PLUGIN_ROOT/tests/hooks/fixtures/status-report-sample.json`; схема:

```json
{
  "project": "Vespera",
  "eyebrow": "Дорожная карта · перед косметикой интерфейса",
  "question": "что доделать, прежде чем наводить красоту",
  "built_at": "2026-09-04",
  "updated_at": "2026-09-04",
  "stale_tasks": 0,
  "next_after": "Косметика интерфейса — после этого",
  "sources": { "analysts": 4, "found": 23 },
  "verdict": {
    "text": "Партнёр не может вернуть задачу в пул: **клиент молча висит**, а ты об этом не узнаёшь. Это перевешивает любую косметику — начинать надо отсюда.",
    "finding_id": "f1"
  },
  "findings": [
    {
      "id": "f1",
      "owner": "code",
      "effort": "M",
      "block": "crit",
      "status": "open",
      "title": "Партнёр может вернуть задачу в пул",
      "what": "Добавлю кнопку «вернуть» и уведомление следующему партнёру.",
      "why": "Сейчас задача, от которой отказались, висит навсегда — клиент ждёт и уходит.",
      "source": "src/tasks/service.py:88; агент 1"
    }
  ]
}
```

Правила:
- Верхний уровень: `project, eyebrow, question, built_at, updated_at, stale_tasks, next_after, sources{analysts, found}, verdict{text, finding_id}, findings[]`. Полей `lead`, `date`, `title`, `stale_merges`, `generated` — нет.
- Находка: `id, owner (code|decision|both), effort (S|M|L|-), block (crit|biz|imp|pol), status (open|done|deferred), title, what, why, source`; необязательные — `task_slug`, `screenshot`, `done_at` (нет значения → поле не пишешь, не `null`).
- `id` — `f1…fN`: новый = максимальный номер в файле + 1. Раз выданный `id` не меняется и не переиспользуется — по нему связаны задача (`task_slug`), снимок (`.forge/reports/shots/<id>.png`) и `render.py link/merged`.
- `built_at` и `updated_at` при полной сборке — сегодня; `stale_tasks` — `0` (после мержей его крутит `render.py merged`).
- Счётчики (N находок → M блоков, K отложено, «чиню я / решаешь ты») НЕ пишешь — их считает рендерер.
- В `.forge` — никаких секретов (правило memory-backup): адреса с паролями, ключи, токены в `what`/`source` не попадают.
- Проверка сразу: `python3 -c "import json;d=json.load(open('.forge/status-report.json'));print(len(d['findings']))"` — печатает число находок. Ошибка → чинишь JSON, не HTML.

**Запись в catalog.** Чтобы отчёт находился через L0, в `.forge/index.yml` нужна запись. Проверь:

```bash
grep -q 'status-report:' .forge/index.yml && echo "есть" || echo "нет — допиши"
```

«Нет» → допиши **последней записью в блоке `catalog:`**, с тем же отступом, что у соседних записей, без `note`:

```yaml
  status-report:
    path: .forge/status-report.json
    tags: [report, what-next, findings, decisions-pending, owner, effort]
```

После этого `wc -c < .forge/index.yml`. Больше 2500 → ничего не ужимай и не спрашивай, одна строка в чат: «index.yml больше 2500 байт — в авто-инжекцию попадает не весь catalog, при необходимости читай файл целиком».

## Шаг 5: Снимки экрана (по возможности, без вопросов владельцу)

**Есть ли что снимать** — решаешь сам, владельца не спрашиваешь, файлы проекта заново не читаешь:
1. Кандидаты (в этом порядке): секция «Адреса интерфейса» из ответа Агента 3 → стандартные `http://localhost:3000`, `http://localhost:5173`, `http://localhost:8000`, `http://localhost:8080`.
2. Живой — первый, где `curl -s -o /dev/null -m 3 -w '%{http_code}' <url>` даёт 2xx/3xx. Только http/https — `file:` в браузере заблокирован.
3. Живого нет → шаг пропущен целиком, без вопросов; в чат одна строка: «интерфейс не запущен — отчёт без снимков; если картинки нужны — запусти проект (или попроси меня) и скажи «добавь снимки»». Приложение сам НЕ запускаешь.

**Что снимать:** только карточки, где `what`/`why` про экран, который владелец видит глазами (форма, кнопка, страница). Не больше 6, в порядке блоков (crit → biz → imp).

**Как снимать (Playwright MCP, инструменты `browser_*`):** один раз `browser_resize` `{width: 1280, height: 800}`; для каждой карточки:
1. `browser_navigate` `{url: <адрес страницы карточки, если знаешь; иначе живой корень>}`
2. `browser_take_screenshot` `{type: "png", filename: ".playwright-mcp/sr-<id>.png", scale: "css"}` — не `fullPage` (документ «читается за 3–5 минут»)
3. Перенос в память проекта:
```bash
mkdir -p .forge/reports/shots && mv .playwright-mcp/sr-<id>.png .forge/reports/shots/<id>.png
```
4. В JSON у находки: `"screenshot": ".forge/reports/shots/<id>.png"` (только путь — рендерер сам встроит картинку; нет файла — карточка без картинки).

После всех снимков — `browser_close`, затем уборка мусора, обязательно, даже если ни один снимок не удался:
```bash
rm -rf .playwright-mcp
```

**Любой сбой** (нет Playwright MCP, отказ в разрешении, таймаут, пустой файл) → продолжаешь без картинки: одна строка в чат, карточка остаётся без `screenshot`, остальные пробуешь дальше. Не больше одной повторной попытки на карточку. Отчёт всегда собирается — с картинками или без.

## Шаг 6: Собрать HTML и открыть

```bash
python3 "$CLAUDE_PLUGIN_ROOT/skills/status-report/render.py" render
xdg-open .forge/status-report.html 2>/dev/null || open .forge/status-report.html
```

Рендерер читает `.forge/status-report.json`, встраивает снимки, считает счётчики, пишет `.forge/status-report.html` (один живой файл, перезаписывается; вместе со снимками сам добавляет себя в `.forge/.gitignore`) и печатает две служебные строки `FORGE-REPORT:` — путь и счётчики. Упал — читай его ошибку: почти всегда поле JSON. HTML руками не правишь никогда.

## Шаг 7: Отчёт в чат (3–5 строк)

```
Отчёт «Что дальше» готов: .forge/status-report.html — открыл в браузере.
Главное: {verdict.text одной фразой}.
{вторая строка вывода render.py — счётчики — БЕЗ префикса «FORGE-REPORT:»}{при 0 снимков: « — интерфейс не запущен; нужны — скажи «добавь снимки» после запуска»}
Первым в код предлагаю: «{title первой открытой карточки crit с owner code}». Скажи «бери» — оформлю задачу. Решения разберём, когда скажешь «давай решения».
```

Числа бери из строки, которую напечатал рендерер, — не пересчитывай руками. Служебный префикс `FORGE-REPORT:` владельцу не показываешь. **ЗАВЕРШИ ХОД** — дождись реакции (как навигатор перед new-task).

## Шаг 8: Хэндофф

| Владелец говорит | Делаешь |
|---|---|
| «бери» / «давай» / «ок» / «первую» | **Инвокни new-task skill** с текстом `card:<id> <заголовок карточки>` (напр. `card:f3 Предоплата списана, а записи нет при обрыве связи`) + одной строкой `what` и `why` как контекст. Метка служебная: new-task после сохранения task-файла свяжет карточку с задачей (`render.py link <id> <slug>` → у карточки появится `task_slug`). Только ОДНА карточка за раз. |
| «вторую» / «не эту, а …» | То же с названной карточкой. |
| «давай решения» | Блок biz, по одной карточке за ход: вопрос из `what` + 2–3 варианта + твоя рекомендация (как навигатор: «не знаю» = твой вариант). Ответ → запись в `.forge/decisions.yml` по правилам session-awareness; у карточки в JSON через Edit `"status": "done"` и `"done_at": "<сегодня>"`; затем `render.py render` (Шаг 6, без нового аудита). Следующая — только после ответа. |
| Ответ на открытое решение **в любой форме и в любой сессии** («по комиссии — пополам», «пусть без регистрации») | То же самое, что строкой выше: записать в `decisions.yml`, закрыть карточку (`done` + `done_at`), пересобрать через `render.py render`. Напоминание при старте сессии пропадёт само. |
| «добавь снимки» | Повторить Шаг 5 (снимки → у карточек `"screenshot"` через Edit) и Шаг 6 — **без нового аудита**: агентов не запускать, находки не менять, `built_at` не трогать. |
| «стоп» / молчит / другая тема | Ничего не двигаешь. Отчёт лежит в `.forge`; при старте следующей сессии хук напомнит одной строкой («ждут N решений, отчёт устарел на M задач»). |

Решения НЕ спрашивай по одному, пока не прозвучало «давай решения». Карточку в работу сам НЕ берёшь.

## Правила языка (как в формате-эталоне)

- От первого лица, на «ты»: «чиню я», «решаешь ты». Не «рекомендуется», не «необходимо».
- Последствия вместо терминов. Стоп-слова без перевода: эндпоинт, миграция, деплой, коммит, мерж, рефакторинг, таймаут, хэндлер, middleware, edge case, регрессия. Нужен термин — переводи в скобках: «вебхук (сообщение, которое банк шлёт нам после оплаты)».
- `title` — то, что владелец увидит или получит, не то, что ты сделаешь в коде.
- Честно: «не реализовано», а не «в процессе»; «не проверял», а не «должно работать».
- Проверка перед записью: прочитал бы это человек с улицы и понял, что сломано и кто это чинит?
