# Мера «по делу»

Правило плагина для всех проектов: не переусложнять и не делать на отъебись. Действует в plan (какие шаги), critique (спор Прагматика и Скептика), execute (как делать шаг и что писать в отчёте) и в чеклисте проверяющего (`skills/requesting-code-review/review-checklist.md`, пункты «перебор?» и «нижняя планка»).

## Перебор — не делаем

- Решение проблемы, которой не было: нет случая из жизни, лога или жалобы.
- Свой скрипт или абстракция там, где хватает правила в тексте или готового инструмента.
- Настройки и флаги «на будущее», которыми никто не пользуется.
- Общий механизм вокруг кода, который используется в одном месте.
- Обработка ситуаций, которые не могут случиться.

## Нижняя планка — без неё работа не сделана

- Логика проверена тестом, который сначала падал.
- Результат проверен живым запуском: есть вывод команды, а не «должно работать».
- Закрыты реальные риски: потеря данных, утечка секретов, деньги, боевой сервер.
- Сбой виден, а не тихий. Тихий откат на худший режим — тоже сбой, о нём говорим.
- Обработаны крайние случаи, которые реально встречаются в этом проекте: пустые данные, нет сервиса или сети, старый формат файлов.
- Нет заглушек и TODO вместо сделанного; не сделанное названо прямо.
- Обновлены доки и память, где этого требует изменение.

## Перед тем как писать код — лесенка

Лучший код — тот, который не написан. Остановись на первой ступени, которая решает задачу целиком:

1. Нужно ли это вообще? Лишнее — не делаем, называем одной строкой.
2. Уже есть в проекте (функция, компонент, сервис, приём)? Берём, как берёт соседний код.
3. Стандартная библиотека языка?
4. Встроено в платформу (браузер, ОС, база, Telegram)?
5. Уже установленная зависимость?
6. Одна понятная строка?
7. Готовая проверенная библиотека, которую можно поставить? Для заметного куска (разбор файлов, даты и часовые пояса, вход и пароли, графики, повторы запросов) — ищем её (Context7, поиск) и берём живую и популярную (обновлялась за последний год, лицензия позволяет), а не пишем своё. Ради пары строк новую не ставим. Новая зависимость — через чекпоинт с владельцем.
8. Только потом — минимум своего.

Лесенка — после того, как прочитан код, который задача затрагивает, а не вместо этого. Ленимся в решении, не в чтении.

## Сознательное упрощение — пометка в коде

Рабочий код с известным пределом помечается одной строкой комментария (`#`, `//`, `--`, `/* */` — по языку):

`упрощено: <что упрощено> — переделать, когда <условие>`

Пишется для владельца-не-кодера: последствия простыми словами, без терминов. Текст уходит в гайд по проекту дословно (группа S).

- Хорошо: `# упрощено: список заказов грузится целиком — переделать, когда заказов станет больше ~5000 (страница начнёт открываться секунды)`
- Плохо: `# упрощено: без пагинации, N+1`

Пометка — не TODO: недописанный код, заглушка, «потом доделаю» пометкой не прикрываются — это по-прежнему «не сделано» из нижней планки.

## Спорный случай

Вопрос-решатель: **«что сломается или кто пострадает, если этого не сделать?»**

- Конкретный ответ из этого проекта → делаем полностью, с тестом и проверкой.
- «Ну мало ли» → не делаем, пишем строкой в идеи.

## Объём ≠ качество

3 строки, закрывающие реальный риск, лучше 100 строк «универсального решения». В отчёте о работе отдельно помечай, что **сознательно не сделано и почему** — чтобы это не выглядело забытым.
