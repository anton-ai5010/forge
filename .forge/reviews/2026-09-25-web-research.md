# Инструменты и приёмы для Forge: интернет-исследование

Дата проверки: 25 сентября 2026. Дополнение к [списку улучшений](../notes/2026-09-25-forge-improvements.md) и [аудиту других проектов](2026-09-25-cross-project-audit.md).

## Вывод и границы проверки

Главная возможность для Forge — использовать появившиеся штатные механизмы Claude Code, добавить точную передачу пользовательских правок и измерять поведение скиллов. Персональная ценность Forge остаётся в понимании запроса Антона, памяти решений, выборе следующего действия и понятном состоянии проекта.

Проверены официальные документации, исходные репозитории и первичные исследования. Наличие функции в документации не доказывает её доступность конкретному аккаунту или установленной версии. Новые инструменты на проектах Антона не запускались; оценки применимости ниже — рекомендации для испытаний, не результаты сравнительного теста.

Локально подтверждено:

- `claude --version`: **2.1.263**.
- `claude plugin validate ./forge-plugin`: прошла проверка **marketplace.json**.
- Отдельный `claude plugin validate ./forge-plugin/.claude-plugin/plugin.json`: прошла проверка **plugin.json**. Это проверка манифестов, не поведения скиллов.
- В установленном skill-creator присутствуют `run_eval.py`, `run_loop.py`, `aggregate_benchmark.py` и HTML-просмотрщик результатов. Их прогоны не выполнялись.
- Forge требует `TodoWrite` в [execute](../../forge-plugin/skills/execute/SKILL.md:98) и других инструкциях. В текущем changelog Claude Code указано отключение этих инструментов по умолчанию для ряда новых моделей. Это реальная точка несовместимости, зависящая от модели и настройки, а не доказанный сбой каждой сессии. [Changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md).

## Что стоит внедрить в первую очередь

### R01. Рецепт запуска и проверки каждого проекта

**Найдено:** встроенные `/run`, `/verify`, `/run-skill-generator`. Они помогают запускать приложение и проверять изменение в работающем продукте; рецепт может сохраняться в проектном скилле. `/verify` может записать удачный способ запуска для следующих сессий. [Документация](https://code.claude.com/docs/en/skills#run-and-verify-your-app).

**Для Forge:** при подготовке проекта сохранять команды запуска, необходимые сервисы, адрес и короткие сценарии проверки. Секреты обозначать ссылками на Bitwarden. Во время выполнения использовать этот рецепт; учитывать правила вызова встроенных команд и их доступность.

**Проверка:** новый чат или чистая рабочая копия запускает приложение по рецепту и проверяет заранее выбранный пользовательский сценарий. Отказ внешнего сервиса остаётся непроверенным пунктом.

### R02. Компактные инструкции и загрузка по необходимости

В статье Anthropic от **24 июля 2026** описан пересмотр инструкций для поколения Claude 5: сокращение повторов, загрузка подробностей по необходимости и сохранение специфичных знаний проекта. Сокращение их системного промпта — внутренний результат Anthropic, не обещание такого же эффекта в Forge. [Статья](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/).

**Для Forge:** проверить пользу длинных блоков Role/Stakes, повторяющихся запретов и обязательных действий при каждом запросе. Например, вымышленный стаж специалиста в [review](../../forge-plugin/skills/requesting-code-review/SKILL.md:8) можно заменить проверяемым заданием ревью. Каталог оставить коротким, подробные процедуры подгружать по задаче.

**Проверка:** сравнить старую и сокращённую инструкции на одинаковых задачах. Сохранить конкретные правила, предотвращающие подтверждённые ошибки. Не удалять инструкции только ради меньшего числа токенов.

### R03. MCP Tool Search и инструкции под установленную версию

Claude Code поддерживает отложенную загрузку MCP-инструментов через Tool Search. Поведение зависит от модели, провайдера и настроек; поддерживаются также исключения для постоянно нужных инструментов. [MCP Tool Search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search).

Интересный практический образец у Vercel: короткий скилл agent-browser направляет агента к `agent-browser skills get core`, который выдаёт инструкции, соответствующие установленному CLI. [Agent-browser](https://github.com/vercel-labs/agent-browser).

**Для Forge:** короткая карта «задача → возможность → доступный инструмент», затем актуальная инструкция выбранного инструмента. Это дополняет F01 и F06. Проверять фактические вызовы на задачах без явного названия инструмента.

### R04. Проверять срабатывание скиллов через имеющийся skill-creator

Официальный skill-creator включает сравнение с базовым вариантом, измерение времени и токенов, просмотр результатов и оптимизацию описания скилла. Для проверки выбора предусмотрены положительные и близкие отрицательные примеры. [Исходник](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md).

**Для Forge:** начать с выбора Context7, браузерного инструмента и глубины процесса. Использовать реальные русские запросы Антона, включая голосовые опечатки. Вопросы с похожими словами, но другой целью, должны проверять ложное срабатывание.

**Проверка:** агент использует документацию там, где она нужна, и не запускает весь pipeline на вопрос «что думаешь о проекте». Отдельная выборка остаётся вне подбора формулировок. Поднять F10 из позднего развития в раннюю часть изменений маршрутизации.

### R05. Совместимость со штатными возможностями вместо фиксированных названий инструментов

Убрать обязательную зависимость от `TodoWrite`: хранить долгую задачу в существующем task/plan-файле, а доступный инструмент отслеживания использовать дополнительно. Не создавать второй обязательный `TASKS.md` с теми же статусами.

Дополнить диагностику проверкой версии, модели, реально доступных инструментов и поддерживаемых возможностей. Использовать штатную диагностику среды; собственная `/forge:doctor` должна проверять специфичное для Forge: память, пути хуков, каталог и маршрутизацию. Системный `/doctor` также упомянут Anthropic как средство проверки инструкций. [Контекст и диагностика](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/).

Frontmatter скиллов теперь позволяет задавать область файлов и изолированный контекст. У `context: fork` нет автоматической истории разговора — такой исполнитель должен получать самодостаточное задание. Это кандидат для ограниченных исследовательских скиллов после проверки совместимости. [Skills](https://code.claude.com/docs/en/skills).

## Инструменты для ограниченного испытания

| Код | Инструмент | Польза для Антона | Что попробовать и что учесть |
|---|---|---|---|
| R06 | **Agentation** | Можно указать элемент на странице и написать «здесь тесно», «эту кнопку перенести». Агент получает техническую привязку к элементу | Один React-проект в режиме разработки; пять правок и браузерная проверка каждой. Компонент добавляется в приложение, MCP связывается с ним отдельно |
| R07 | **Vercel agent-browser** | Ещё один кандидат на простой браузерный CLI с компактными снимками и работой с Chrome | Сравнить с Browser Harness на одинаковых сайтах, затем выбрать основной. Уже поддерживает CLI-инструкции своей версии; способы подключения к живому браузеру и копии профиля различаются |
| R08 | **ast-grep + официальный skill** | Поиск конструкций кода и массовые изменения: конкретные вызовы, параметры, вложенные конструкции | Использовать для поиска по структуре и повторяющихся ошибок. Для имени файла или строки оставить обычный `rg`; сначала проверить правило на положительном и отрицательном примерах |
| R09 | **Worktrunk** | Удобное управление несколькими рабочими копиями и видимость активности агентов | Вводить при реальной параллельной работе над ветками. Интеграции Claude Code и Codex имеют разные возможности; согласовать хуки с Forge |
| R10 | **RTK** | Сокращение шумного вывода команд перед передачей модели | Пилот на длинных тестовых логах; сохранять доступ к полному выводу, сравнивать время и успешность всей задачи |

Источники и существенные детали:

- **Agentation:** аннотации содержат селекторы и, когда страница предоставляет сведения, пути исходников, компоненты и стили. Возможна передача вручную или через MCP. [Возможности](https://www.agentation.com/), [установка](https://www.agentation.com/install). В Forge закрывать замечание только после проверки исправления; наблюдение за новыми замечаниями включать отдельным режимом. [MCP](https://www.agentation.com/mcp). Лицензия различает внутреннее использование и распространение внутри продаваемого продукта; способ интеграции должен это учитывать.
- **Agent-browser:** подключение к существующему Chrome и восстановление сессии требуют выбора подходящего режима. Предлагается как альтернативный основной браузерный инструмент для сравнения с Browser Harness. [Репозиторий](https://github.com/vercel-labs/agent-browser).
- **Ast-grep:** авторы отдельно предупреждают, что установка скилла делает его обнаруживаемым, но не гарантирует предпочтение при выборе. Для Forge это ещё одно подтверждение необходимости маршрутизации и её проверки. [Официальный skill](https://github.com/ast-grep/agent-skill).
- **Worktrunk:** существуют интеграции нескольких агентов, а автоматизация жизненного цикла worktree зависит от доступных хуков конкретной среды. [Документация](https://worktrunk.dev/claude-code/).
- **RTK:** фильтрует вывод CLI; заявленные проценты относятся к этому выводу, а не к полной стоимости сессии. [Репозиторий](https://github.com/rtk-ai/rtk), [объяснение метрик](https://github.com/rtk-ai/rtk/blob/develop/docs/guide/resources/savings-explained.md). Последняя ссылка относится к ветке `develop`; выбранный релиз перед установкой нужно проверить отдельно.

Браузерная связка из предыдущего предложения сохраняется как основной кандидат: Browser Use/Harness, DevTools, Playwright Test и резервный MCP. Agent-browser добавляется в сравнение, а не объявляется победителем без испытания.

## Новые процессы, которые можно взять из Claude Code

### R11. Цель с проверяемым завершением

Штатный `/goal` продолжает работу между ходами до выполнения условия либо остановки по предусмотренной причине. Его отдельный оценщик читает свидетельства из разговора и сам не запускает тесты. Режим разрешений от установки цели не меняется. [Документация](https://code.claude.com/docs/en/goal).

**Для Forge:** предлагать этот режим для уже определённой длительной задачи. Условие связывать с критериями и результатами реальных проверок. Автоматическую продолжительность ограничивать по договорённости; не считать текстовое ограничение времени жёстким техническим лимитом.

**Проверка:** воспроизведение дефекта → исправление → повторная проверка. Цикл заканчивается с доказательством либо конкретным препятствием. Он не заменяет пользовательскую приёмку и не нужен каждому короткому вопросу.

### R12. Сохранённые workflows для повторяющейся тяжёлой работы

Dynamic workflows позволяют сохранять оркестрацию в JavaScript и поставлять её в `workflows/` плагина. Среда управляет исполнителями и возобновлением. [Документация](https://code.claude.com/docs/en/workflows#distribute-a-workflow-in-a-plugin).

**Кандидаты Forge:** большой аудит с перепроверкой находок; однотипная миграция независимых частей; обработка серии сессий для поиска повторяющихся исправлений пользователя. Сначала один ограниченный сценарий со структурированным результатом.

В официальной статье от **2 июня 2026** этот механизм предлагается для сложных задач и прямо отмечается дополнительный расход токенов. Поэтому постоянный `ultracode` для каждого запроса не входит в рекомендацию. [Описание подхода](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/).

## Дополнительные находки: браузер, рабочие ошибки и интерфейсы

### R13. Проверить штатный Claude in Chrome до выбора дополнительного браузерного инструмента

Интеграция Claude Code с Chrome использует входы пользователя в сайты и позволяет работать с формами, страницами и консолью. Есть собственная диагностика `/chrome`. Требуются расширение, прямой план Anthropic и вход через `/login`; API-ключ и `setup-token` эту интеграцию не включают. [Документация](https://code.claude.com/docs/en/chrome).

**Для Forge:** при выборе основного браузера сначала учитывать уже доступную штатную интеграцию. Если она закрывает обычную работу в кабинетах, дополнительный браузерный слой может не понадобиться. DevTools остаётся кандидатом для углублённой диагностики, Playwright Test — для повторяемых тестов. Подключение Chrome к аккаунту Антона здесь не проверялось.

### R14. Sentry: агент получает контекст ошибки работающего приложения

Есть официальный Sentry-плагин для Claude Code: настройка SDK, разбор ошибок через MCP и ревью с контекстом Sentry. Полезна и его организация: небольшой набор маршрутизирующих скиллов, остальные процедуры подгружаются по необходимости. [Плагин](https://github.com/getsentry/plugin-claude), [MCP](https://github.com/getsentry/sentry-mcp).

**Для Forge:** если проект уже отправляет ошибки в Sentry, разбор начинается с конкретного события, версии и трассы. Затем агент сопоставляет их с кодом, воспроизводит проблему и проверяет исправление. Это особенно применимо к Витрине, где Sentry фигурирует в изученной памяти. Живая конфигурация проекта не проверялась.

**Проверка:** одна известная ошибка из истории → подтверждённая причина → локальная проверка исправления. Предположение Seer считать гипотезой до подтверждения; новые платные автоматизации не требуются для первичного пилота.

### R15. React Grab: быстрый способ указать нужный компонент

React Grab передаёт выбранный элемент и стек React-компонентов с расположением исходника. Это кандидат для простого сценария «укажи вот это место»; Agentation лучше соответствует сценарию списка обсуждаемых замечаний. Второе — моя оценка по устройству инструментов, сравнительных запусков здесь не было. [React Grab](https://github.com/aidenybai/react-grab).

**Пилот:** выбрать один способ визуальной обратной связи для одного React-проекта. Измерить число неверно выбранных компонентов и время до принятой правки. Рекламные множители скорости не переносить на проекты Антона без замера.

### R16. React Doctor: дополнительные проверки React-проектов

Инструмент статически проверяет React-код; в CI может выделять проблемы, внесённые конкретным изменением. Есть отдельная возможность собрать профиль работающего приложения. [Официальный репозиторий](https://github.com/millionco/react-doctor).

**Для Forge:** дополнительный маршрут только для React. Начать с отчёта по изменённому коду, оценить полезные находки и ложные срабатывания. Балл инструмента не использовать как критерий готовности продукта и не исправлять весь старый код в рамках небольшой задачи.

### R17. WebMCP: наблюдать и экспериментировать на своём сайте

WebMCP позволяет сайту объявить структурированные действия для агента: например, поиск или запуск диагностики. По официальной документации, обновлённой **7 августа 2026**, механизм находится в origin trial начиная с Chrome 149; предусмотрен флаг для локальной разработки. Это развивающийся веб-стандарт, не универсальный уже установленный MCP-сервер. [Chrome for Developers](https://developer.chrome.com/docs/ai/webmcp?authuser=09).

**Для Forge:** необязательный эксперимент для собственного приложения, где регулярные действия агента оправдывают явный интерфейс. Обычную работу с чужими кабинетами на него пока не завязывать. Принимать решение после проверки поддержки выбранного браузера и агента.

## Короткие правила и промпты для Forge

Это предложенные формулировки для тестирования, а не изменения действующих инструкций. Они адаптированы к запросам Антона. Свежий материал Anthropic от **22 сентября 2026** рекомендует задавать результат, условия остановки и продолжать работу без лишних приглашений «продолжить». Советы зависят от поколения модели. [Руководство](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/).

### P01. Доведение порученной работы

> Сохраняй исходную цель и критерий готовности. Выполняй следующие необходимые действия, пока они входят в порученную работу. Обновление статуса сопровождай следующим действием. Обращайся ко мне, когда нужен мой выбор или разрешение, которого ещё нет. В финале покажи результат, проверку и оставшееся препятствие.

### P02. Выбор инструмента

> Определи, какая возможность нужна, и проверь доступные инструменты. Для документации библиотеки используй Context7 с версией проекта; при отсутствии подходящих сведений — официальные документы. Для сайта выбери браузер, для диагностики приложения — DevTools, для повторяемой проверки — тест проекта. Не объявляй инструмент использованным без результата вызова.

### P03. Проверка результата

> Преврати критерий готовности в наблюдаемую проверку. Для ошибки сначала получи воспроизведение, затем проверь тот же сценарий после исправления. Разделяй успешные, неуспешные и невыполненные проверки. Сохрани команду или сценарий, среду и результат.

### P04. Ревью с доказательствами

> Проверь изменение по критерию задачи и найди конкретные условия, при которых оно даст неправильный результат. Для каждой находки укажи место, сценарий и подтверждение. Если подтверждения нет, обозначь гипотезу. Отсутствие находок допустимо; количество замечаний не является целью.

Разделение исполнителя и проверяющего — исследованный Anthropic приём, но отдельный модельный проверяющий также может ошибаться. Применять его по риску вместе с наблюдаемыми проверками. [Harness design, 24 марта 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps).

### P05. Возобновление после перерыва

> Прочитай цель, текущую задачу и следующий шаг. Сверь актуальность с рабочими файлами и последними изменениями. Сохраняй принятые решения, пока новые сведения их не опровергают. Продолжи с первого незавершённого действия; противоречия памяти отметь явно.

### P06. Повторяющееся исправление пользователя превращать в проверку

> Когда одна и та же правка повторяется, сохрани конкретный пример ошибки и ожидаемый результат. Выбери место проверки: команда проекта, тематический скилл или хук. Проверь правило на случае, где оно должно сработать, и похожем случае, где оно мешало бы. Не распространяй частное предпочтение на все проекты.

В материале Anthropic от **22 июля 2026** описано превращение повторяемых ручных проверок в verification skills, привязанных к соответствующему процессу. Для Forge это уточнение `evolve` и `hookify`: выбирать подходящее место контроля, а не каждый раз расширять общий список инструкций. [Verification loops](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills).

## Как оценивать ускорение

Два свежих исследования полезны как ограничения ожиданий:

- **Token Reduction Is Not Cost Reduction**, версия от 12 августа 2026: в исследованной конфигурации сильное сжатие уменьшило доставленные токены вывода на 38,4%, но увеличило выставленную стоимость на 6,8%. Это результат конкретного эксперимента, а не универсальная оценка RTK. Авторы показывают роль кэширования и дополнительных действий агента. [Работа](https://arxiv.org/abs/2607.12161).
- **Skill Issue**, 11 сентября 2026: на трёх Kotlin-репозиториях улучшенные инструкции выглядели полезными, однако прирост одной из оптимизаций нельзя было надёжно отделить от разброса запусков при данном объёме задач. Красивый скилл требует поведенческой проверки. [Работа](https://arxiv.org/abs/2609.12742).

Для Forge измерять: завершён ли исходный сценарий, сколько было напоминаний Антона, время до результата, переделки после «готово», расход при наличии достоверных данных. Повторять часть задач и оставлять контрольную выборку. Небольшой пилот помогает отсеять плохие идеи, но не доказывает универсальное превосходство.

## Порядок внедрения после согласования отдельных задач

1. Проверка возможностей среды, устранение зависимости от TodoWrite, правила выбора инструментов и сокращение повторов. Одновременно небольшие тесты выбора скиллов через уже имеющийся skill-creator.
2. Один проектный рецепт запуска и проверки; один пилот Agentation или React Grab на интерфейсе. Для проекта с действующим Sentry — разбор одной известной ошибки через официальный инструмент.
3. Проверка доступности штатного Claude in Chrome, затем сравнение подходящих браузерных вариантов на одинаковых задачах. DevTools и Playwright Test остаются отдельными диагностической и тестовой ролями.
4. Один сохранённый workflow для доказанно повторяющейся тяжёлой задачи. Ast-grep подключать для структурных изменений, Worktrunk — для параллельных веток, RTK — только по результатам замера.

Из предыдущего списка меняется приоритет: F10 нужен уже при F01, а F06 следует строить поверх штатной диагностики с собственными проверками Forge. Добавлены конкретные R01–R17 и P01–P06 для последующих задач. Производственные файлы плагина и настройки инструментов в этом исследовании не изменялись.
