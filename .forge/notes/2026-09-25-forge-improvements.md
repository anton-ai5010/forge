# Предложения по развитию Forge

Дата: 25 сентября 2026. Статус: предложенный список изменений, ещё не утверждённый план реализации.

Основание: [аудит Forge в 14 папках проектов](../reviews/2026-09-25-cross-project-audit.md), проверка исходников плагина и официальной документации инструментов. Приоритеты ниже — моя рекомендация; сравнительные испытания новых инструментов на задачах Антона ещё не проводились.

## Направление

Развивать Forge как персональный рабочий процесс: агент помнит цель, самостоятельно выбирает доступные инструменты, доводит задачу до проверяемого результата и понятно объясняет состояние владельцу. Сохранить русское общение, решения с объяснением причин, историю неудачных подходов и гайд проекта.

### Как должна работать автоматическая маршрутизация

1. Понять действие и ограничения: библиотека и версия, обычный сайт или отладка приложения, нужная машина и браузерная сессия.
2. Сопоставить действие с реально доступными инструментами текущей среды. Настройка в Claude Code не доказывает доступность в Codex и наоборот.
3. Загрузить короткую инструкцию выбранного инструмента. Общий каталог держать компактным; подробности читать по необходимости.
4. Использовать инструмент без отдельного напоминания пользователя в пределах уже порученной работы.
5. При недоступности перейти к подходящему запасному варианту. Сообщить об ограничении, если оно влияет на результат. Не считать попытку вызова успешной проверкой.
6. Сохранить существенное свидетельство результата: источник документации, вывод проверки, ссылку на артефакт. Не писать в журнал секреты, cookies и полное содержимое личных кабинетов.

Для Context7 конкретное правило: при необходимости документации библиотек агент обращается к нему самостоятельно, сверяет версию с проектом и использует официальные источники при пробеле или несоответствии. Уже полученные подходящие сведения можно повторно использовать в пределах задачи. У Context7 есть MCP и CLI + Skills, а официальная инструкция прямо предусматривает автоматический вызов по правилу. [Context7](https://github.com/upstash/context7).

Сам текст правила не гарантирует поведение модели: маршрутизацию нужно проверять сценариями F10 и наблюдаемыми вызовами. Жёсткие технические условия, которые можно проверить программно, следует проверять программно.

### Уточнение браузерной схемы

Предложенное разделение ролей разумно. Для личного Chrome у Browser Use есть отдельный Browser Harness: он подключается к реальному браузеру, а локальный режим предназначен в том числе для уже авторизованной работы. Выбирать следует конкретный способ подключения; облачный браузер не нужен по умолчанию. [Browser Harness](https://github.com/browser-use/browser-harness).

Chrome DevTools for Agents предоставляет console, network, трассы производительности и управление Chrome; доступны MCP и CLI. Это подходящий основной инструмент диагностики приложения. [Chrome DevTools](https://github.com/ChromeDevTools/chrome-devtools-mcp).

Playwright MCP оставляем резервом интерактивной работы. Его разработчики также предлагают CLI + Skills для coding-агентов, когда важна экономия контекста. Для воспроизводимых тестов с проверками результата нужен отдельный Playwright Test: управляемые моделью клики сами по себе не гарантируют одинаковый сценарий при повторном запуске. [Playwright MCP](https://github.com/microsoft/playwright-mcp), [Playwright Test](https://playwright.dev/docs/intro).

Это предпочтения по задачам, а не взаимоисключающие возможности продуктов. При смене управляющего инструмента передавать выбранную вкладку и цель проверки; не управлять одной вкладкой одновременно несколькими агентами. Если приложению на домашнем ПК нужен локальный Chrome мака, явно решать доступ к адресу, не считать два `localhost` одной машиной.

## Что уже настроено

- В `~/.claude/settings.json` включены `context7@claude-plugins-official` и `playwright@claude-plugins-official`; найдены соответствующие записи установки и MCP-конфигурации. Их живые вызовы в Claude Code в этой проверке не выполнялись.
- В Forge Context7 уже фигурирует в `new-task`, `plan` и `forge-context`. Поэтому требуется проверяемое поведение и единое правило, а не ещё одно случайное упоминание.
- В текущей сессии Codex именованные инструменты Context7, Browser Use, DevTools и Playwright не обнаружены среди доступных вызовов. Доступность других средств браузера нужно учитывать отдельно.
- Одноимённые CLI не найдены в текущем PATH. Это не исключает запуск через `npx`/`uv` или другую установку.
- В локальном `.codex/hooks.json` обнаружен путь `/home/anton/...` от Linux-машины. Поддержку разных сред нужно проверять фактическим запуском, а не переименованием документации.

## Очерёдность

**Первая партия:** F03 и F05 — локальные исправления известных дефектов; F01 и минимальная диагностика F06 — самостоятельный выбор уже имеющихся инструментов. Затем F02 — подключение браузерных средств с проверкой на трёх реальных сценариях. Проверки этих изменений входят в соответствующие задачи сразу.

**Вторая партия:** F04, F07, F08 и F09 — актуальное состояние, доказательства результата, сокращённый процесс и управляемая глубина исследования.

**Третья партия:** полноценный корпус F10, перенос старых проектов F11 и сокращение дублирования F12. Сравнить текущий и упрощённый Forge на 6–10 сопоставимых задачах; фиксировать напоминания владельца, время, переделки и расход, если доступен. Это пилотное сравнение, а не статистическое доказательство.

OpenSpec и свежий Superpowers оставить кандидатами для такого сравнения. Их возможности и источники разобраны в исходном аудите; решение о замене всего процесса пока не обосновано результатами на проектах Антона.

## Дополнение после интернет-исследования

[Новые инструменты, штатные возможности Claude Code и шесть предложенных промптов](../reviews/2026-09-25-web-research.md).

Уточнение приоритетов: проверки выбора скиллов F10 нужны уже при F01; F06 следует дополнить штатной диагностикой Claude Code. Добавлены рецепт запуска через `/run` и `/verify`, проверка совместимости с инструментами отслеживания задач, пилот Agentation, сравнение agent-browser с Browser Harness и сохранённые workflows для повторяющихся тяжёлых задач. RTK и Worktrunk остаются условными кандидатами под измеренную потребность.

Дополнительно: учитывать доступный Claude in Chrome до выбора браузерного слоя, Sentry — для разбора ошибок работающего приложения, React Grab — как вариант точной передачи элемента интерфейса. React Doctor применять по стеку; WebMCP пока оставить экспериментальным направлением.
