# Модели и расходы: экономия недельного лимита без потери качества

Источник: `.forge/notes/2026-10-12-limit-economy-office-prorab.md` (разделы 1, 2, 5, 7, 14), решения `cost-plan-order`, `fast-path-small-changes`, `no-jev-model-router`, backlog `direction.yml` «Модели и расходы».

Контекст: подписка — важен недельный лимит, не деньги. С пн 2026-10-12 ушло 26% лимита за ~1.3 дня, ~70% — чат-исполнитель integration: схема «impl → 2–3 review на Opus → fix → re-review → final-review», 56 из 108 помощников — проверяющие по 80–100 шагов (заново изучают проект). Схему плагин не задаёт — чат integration сам пишет воркфлоу (`~/.claude/projects/-Users-mac-Projects-Ya--Market-integration/*/workflows/scripts/`); модель/effort в них и у большинства помощников плагина не указаны → наследуют Opus.

## Задача
Срезать расход недельного лимита на помощниках без потери качества: проверка кода — Sonnet + Codex, Opus — только для важного; проверяющим — готовый дифф вместо «изучи проект»; за каждой ролью плагина закреплены модель и effort. Пилот на integration, замер «до/после». Затем — сжиматель логов, гигиена основного чата, подсказки effort/ultracode.

## Критерий готовности

**Срочное:**
- В плагине есть таблица «роль → модель + effort + почему» по всем помощникам (типы агентов в `agents/`, критики, сборщики гайда, картографы, помощники execute, проверяющие). Три ступени: **Haiku** — механика (поиск, списки, подсчёты, формат, запасной сжиматель логов) — только если прошёл проверку ниже; **Sonnet** — проверка, исследование, документация, 2 из 4 критиков; **Opus** — план, трудные решения, финальная проверка. Ни один помощник не наследует модель основного чата молча; Fable — только по явному решению.
- Правила execute/ревью: на шаг — один проверяющий Sonnet + Codex (`codex exec -s read-only`, получает только дифф + задачу + критерий, запускается в пустой папке без доступа к проекту — `.env` не утекает). Финальный Opus — только если шаг трогает цены, оплаты, заказы, закупки, боевой сервер, удаление данных, или Sonnet и Codex разошлись. Нет Codex → один Sonnet, работа не встаёт. Codex выключается в `.forge` проекта.
- Проверяющий получает дифф + текст задачи + критерий шага и может читать соседний код (кто вызывает изменённое), с потолком ~30 шагов; на пробном прогоне укладывается в ≤30 шагов вместо 80–100 (видно по логам).
- Находки проверяются пачкой: один проверяющий подтверждает/опровергает все находки одним заходом, а не «отдельный скептик на каждую находку» (в integration это давало до 36 помощников на одну проверку — `stage2-block-f-review` 4 искателя × до 8 находок).
- В воркфлоу, которые Claude пишет по правилам плагина, у каждого `agent()` указаны model и effort — проверка на новом воркфлоу integration после пилота.
- **Условие выпуска** — сравнение качества на 2–3 старых шагах integration: новая схема находит те же настоящие проблемы, что старая. Если пропущен хоть один критичный баг, найденный старой схемой, — в этом месте остаётся Opus / проверка находок по одной; правила выходят только после сравнения. Плюс 3 типичные мелкие задачи из integration — Haiku vs Sonnet: без ошибок у Haiku → механика за ним, иначе за Sonnet. Таблица сравнения — в `.forge/notes/`.
- Замер `.forge/notes/2026-10-12-scripts/week.py` до и после пилота: доля проверяющих в расходе падает минимум вдвое; цифры записаны в заметку.

- Мера «по делу» (не переусложнять и не делать на отъебись: признаки перебора, нижняя планка, вопрос «что сломается, если не сделать?») — правило плагина: есть в plan / execute / critique и в чеклисте проверяющего, действует во всех проектах.

**Документация по Прорабу (все 9 пунктов раздела 11 заметки 2026-10-12; делается, пока идёт пилот):**
- Иерархия правды и «где какая правда» записаны в правилах загрузки памяти; таблица «что изменил → что обновить» есть в conventions плагина, проверяющий сверяется с ней.
- «Не делать» из index.yml доходит до Claude целиком даже при обрезке до 2500 байт.
- У решений стабильные коды D-NN; устаревшее помечается «заменено D-X», а не удаляется.
- Большие файлы памяти (>20k символов) грузятся оглавлением + нужная запись по коду; decisions integration в оглавлении ≤15% размера.
- Проверка расхождений код/доки находит в плагине мёртвый `lib/` и «33 vs 35 скиллов»; расхождения пишутся в `status.yml` → `drift:`; при старте сессии строка «расхождений N / доки без правки M дней» (только если есть что сказать), аналитик гайда берёт их в риски.
- Журнал сессий пишется отдельными файлами-фрагментами, правило «записей >7 — удали старые» убрано.

**После срочного:**
- Сжиматель логов: сначала проверить RTK; длинный вывод команды → краткий пересказ Qwen 3.8 (если есть Ollama), иначе Haiku; сырой вывод остаётся доступен; логи с секретами — только локально.
- Гигиена основного чата: длинные выводы уходят помощнику; при разросшейся памяти плагин предлагает продолжить в новом чате.
- Подсказки: в начале фазы одна строка про `/effort` (разбор/план/критика — high, реализация — medium, мелочи — low) и ultracode для важных задач.

Выпуск осторожный: всё выключаемо в `.forge` проекта; Codex/Ollama — только если установлены.

## Доработано на разборе
- Главный множитель расхода — не 2–3 проверяющих, а «отдельный скептик на каждую находку» → проверка находок пачкой. Проверяющему не «только дифф»: для кода с деньгами нужен соседний код (вызовы, пробы) → дифф + задача + критерий + чтение соседнего кода с потолком ~30 шагов.
- Сравнение качества — условие выпуска, а не финальная галочка (Sonnet на коде с деньгами и пачечная проверка — непроверенные допущения). Временную заплатку в память integration не делаем — ждём выход плагина.
- По слову владельца в задачу вошли все 9 пунктов документации из Прораба (раздел 11 заметки) — раньше планировались в «Порядок в памяти». Делаются в окне пилота, чтобы не задержать выпуск экономии.
